02입력 자료 분석

테스트 DB (8-bit grayscale TIFF)

DBiType해상도 (W×H)구성파일명
FVC2000_DB3_B1448 × 47810손가락 × 8장 = 80장101_1.tif ~ 110_8.tif
FVC2002_DB3_B2300 × 30010 × 8 = 80장동일
FVC2004_DB1_B2640 × 48010 × 8 = 80장동일

평가 프로그램은 TIFF를 디코딩해 헤더 없는 raw 픽셀 버퍼(1 byte/pixel, 좌상단부터)로 DLL에 넘긴다.

확인 필요: FVC2002_DB3_B와 FVC2004_DB1_B는 iType이 둘 다 2인데 해상도가 다르다. DLL 함수에는 이미지 크기 인자가 없어 DLL이 크기를 알 방법이 없다. 10주차 안에 교수님께 질의한다.

DLL 규격 (안내서 p26–29, 예제 BioApi.h)

extern "C" __declspec(dllexport)
int KISA_Enroll (int iType, unsigned char* pImage, unsigned char* pEnroll,
                 int* piEnrollSize, int* piErrorCode, char arErrorMessage[256]);
int KISA_Attempt(int iType, unsigned char* pImage, unsigned char* pAttempt,
                 int* piAttemptSize, int* piErrorCode, char arErrorMessage[256]);
int KISA_Compare(unsigned char* pEnroll, unsigned char* pAttempt,
                 double* pdScore, int* piErrorCode, char arErrorMessage[256]);
  • 반환값: 성공 1, 실패 0 이하. 실패 시 에러코드와 메시지를 로그에 기록
  • 템플릿 크기 < 1,000,000 byte, 점수는 0(타인)~1(동일), 소수 셋째 자리까지. 범위 밖 점수는 비교 거부(FNMR에 반영)
  • KISA_Compare에는 템플릿 크기가 넘어오지 않으므로 템플릿 헤더에 크기·버전을 담는다
  • 부속 파일은 DLL과 같은 폴더에 두고 GetModuleFileName(g_hDLL)로 경로를 구한다 (안내서 p31)
  • 예제 DLL은 VC2005/2010 프로젝트라 32bit(x86)일 가능성이 높다. 평가 프로그램은 x86/x64 DLL을 모두 로드할 수 있어야 한다

시험 조합 규모 (DB 1개, 동일 이미지 비교 제외)

규칙계산시도 수
본인비교, 모든 조합 (순서 있음)10 × 8 × 7560
본인비교, 대칭 제거 (FVC 방식)10 × C(8,2)280
타인비교, 모든 조합80 × 725,760
타인비교, 각 손가락 첫 1장끼리10 × 990 (대칭 제거 45)

공개 DB는 작아서 전수 평가도 수 초~수 분이면 끝난다. 실제 K-NBTC DB(센서당 7,500장)를 고려해 병렬·부분 평가 구조를 갖춘다.

EER 추정 (FVC 정의)
t1 = max{ t | FNMR(t) ≤ FMR(t) }, t2 = min{ t | FNMR(t) ≥ FMR(t) }. FMR(t1)+FNMR(t1) ≤ FMR(t2)+FNMR(t2)이면 [EERlow, EERhigh] = [FNMR(t1), FMR(t1)], 아니면 [FMR(t2), FNMR(t2)]. EER = (EERlow + EERhigh) / 2.

프로세스 격리 구조

평가 대상 DLL이 crash하거나 무한 루프에 빠져도 평가 프로그램은 살아 있어야 한다. 그래서 DLL은 별도 Worker 프로세스에서만 로드한다.

  • Timeout: 작업별 마감 시각 감시 → 초과 시 TerminateProcess, TIMEOUT 기록 후 Worker 재기동
  • Crash: 프로세스 종료·파이프 끊김 감지 + Worker 내부 SEH(__try/__except)로 예외 코드 기록
  • 강제 종료: 중지 버튼 → 모든 Worker 종료, 지금까지 결과는 보존해 이어하기 가능
  • 병렬: Worker 개수 = 사용자가 지정한 동시 수행 수
  • bitness 자동 판별: DLL의 PE 헤더(Machine 필드)를 읽어 x86/x64 Worker 선택

05지문인식 알고리즘 DLL

처리 과정 (미뉴셔 기반)

  1. iType → (W, H) 표로 이미지 크기 결정 (질의 결과 반영)
  2. 정규화(평균·분산), 블록 단위 전경 분할
  3. gradient 기반 방향장 + 융선 주파수 추정
  4. Gabor 필터 강조 → 이진화 → 세선화(Zhang–Suen)
  5. Crossing Number로 끝점·분기점 추출 (위치·방향·품질)
  6. 거짓 미뉴셔 제거: 경계 근처, 짧은 가지, 너무 가까운 쌍
  7. 템플릿 직렬화 [magic|version|W|H|count|minutiae…] (수 KB)
  8. 매칭: Hough 투표로 회전·이동 정렬 → 허용 오차 안 대응점 수 → 0~1 점수 (소수 3자리)
  9. 개선 단계: 로컬 디스크립터(MCC 계열)나 이웃 미뉴셔 구조 매칭으로 교체·병합

품질 기준

  • 어떤 입력에도 crash 없음. 실패 시 0 반환과 의미 있는 에러코드
  • 전역 상태 없이 스레드 안전 (병렬 평가 대응)
  • 부속 파일 없는 단일 DLL 원칙, x86/x64 둘 다 빌드
  • 내부 목표: 3개 DB 평균 EER 10% 이하 → 개선 단계에서 5% 이하
