02평가 전체 흐름

"평가 시작" 버튼을 누르면 아래 6단계가 순서대로 진행된다. 각 단계는 진행률 표시줄에 단계명으로 표시된다.

STEP 0사전 검증 (Validate)

  • DLL 파일 존재 확인, PE 헤더의 Machine 필드로 x86/x64 판별 → 사용할 Worker 결정
  • Worker 1개를 띄워 HELLO 전송 → DLL 로드 및 KISA_Enroll/Attempt/Compare 3개 export 확인. 하나라도 없으면 오류 대화상자 후 중단
  • DB 폴더 스캔: {손가락ID}_{순번}.tif 형식만 채택, 형식이 틀린 파일은 경고 목록에 표시
  • 모든 이미지 크기가 같고, iType의 기대 크기(설정 표)와 맞는지 확인
  • 출력 폴더 쓰기 권한 확인, 결과 폴더 <DB명>_<yyyyMMdd_HHmmss> 생성

STEP 1이미지 캐시 (Prepare)

  • TIFF를 디코딩해 헤더 없는 8-bit raw 파일로 cache/에 저장 (W×H 바이트, 좌상단부터)
  • Worker는 TIFF를 몰라도 되고, 같은 이미지를 여러 번 디코딩하지 않는다

STEP 2평가 계획 생성 (Plan)

  • 등록 규칙 → 등록 이미지 집합 E, 본인·타인 규칙 → 비교 쌍 목록 G, I
  • 비교에 쓰이는 이미지 집합 A (각 쌍의 비교 쪽 이미지)를 모아 Attempt 추출 대상으로 삼는다
  • 동일 이미지 쌍 제거, 중복 쌍 제거
  • seed로 작업 순서를 섞는다 (5장 참고). 계획 전체를 plan.json, pairs_genuine.csv, pairs_impostor.csv로 저장
  • 부분 평가 모드면 규칙 대신 사용자가 준 쌍 파일을 읽어 G, I를 만든다

STEP 3특징 추출 (Enroll + Attempt)

  • E의 각 이미지 → ENROLL 작업, A의 각 이미지 → ATTEMPT 작업. 두 종류를 섞은 무작위 순서로 Worker들에 분배
  • 성공하면 템플릿을 templates/E_101_1.tpl, templates/A_101_2.tpl로 저장하고 log_enroll.csv에 한 줄 기록

STEP 4비교 (Compare)

  • G ∪ I의 각 쌍 → COMPARE 작업 (무작위 순서, genuine/impostor 섞임)
  • 등록 템플릿이 없으면 DLL을 호출하지 않고 SKIP_EF로 기록 (NEF에 집계)
  • 비교 템플릿(Attempt)이 없으면 SKIP_AF로 기록, matching 실패(NMF)로 집계
  • 결과는 log_match.csv에 한 줄씩 기록

STEP 5지표·리포트 (Report)

  • 두 로그 CSV만으로 지표를 계산한다 (그래서 나중에 로그만 가지고 리포트 재생성 가능)
  • 선택된 항목만 HTML·DOCX에 담고, 그래프는 figures/에 SVG와 EMF로 따로 저장
Enroll과 Attempt를 분리하는 이유: 규격상 비교는 "등록 템플릿(KISA_Enroll) ↔ 인식 템플릿(KISA_Attempt)"이다. 같은 이미지라도 Enroll과 Attempt 결과는 다를 수 있으므로 각각 따로 추출해 저장한다.

03Worker 동작

생명주기

  1. GUI가 CreateProcess로 실행: FPWorker32.exe --pipe \\.\pipe\fpeval_<pid>_<slot>. 모든 Worker는 GUI가 만든 Job Object(KILL_ON_JOB_CLOSE)에 넣어, GUI가 죽으면 같이 종료된다
  2. 파이프 연결 → HELLO{dllPath} 수신 → SetDllDirectory(DLL 폴더) 후 LoadLibrary, GetProcAddress 3개 → 결과 응답
  3. 명령 루프: 요청 1개 받기 → 실행 → 응답 1개 보내기 (한 번에 작업 하나)
  4. QUIT 수신 시 FreeLibrary 후 종료

명령 하나를 처리하는 순서 (ENROLL 예)

  1. cache/101_1.raw를 읽어 가드 페이지 버퍼에 넣는다: VirtualAlloc로 (이미지 크기를 페이지 단위로 올림 + 1페이지)를 잡고, 마지막 페이지를 PAGE_NOACCESS로 바꾼 뒤 이미지 끝이 가드 페이지 바로 앞에 오도록 배치. DLL이 이미지 범위를 넘어 읽으면 즉시 Access Violation이 난다
  2. 출력 버퍼: 1,000,000 바이트 + 4,096 바이트 canary(고정 패턴 0xCD)
  3. QueryPerformanceCounter → __try { ret = KISA_Enroll(...) } __except(...) → 시간 측정 종료
  4. 검사: 반환값, 크기 범위(0 < size < 1,000,000), canary 훼손 여부
  5. 성공이면 템플릿을 outPath에 정확히 size 바이트만 저장
  6. 응답: {status, retVal, errCode, errMsg[256], size, elapsedUs}

COMPARE는 두 템플릿 파일을 읽어 각각 "파일 크기만큼 + 가드 페이지" 버퍼에 넣고 KISA_Compare를 호출한다. 점수가 NaN이거나 [0,1] 밖이면 MISMATCH. 점수는 소수 셋째 자리까지 그대로 기록한다(반올림은 지표 단계에서 옵션).

예외가 났을 때

SEH로 예외를 잡으면 예외 코드(예: 0xC0000005)를 담아 CRASH 응답을 보내고 스스로 종료한다. DLL 내부 상태가 망가졌을 수 있으므로 같은 프로세스를 재사용하지 않는다. 응답조차 못 보내고 죽으면 GUI 쪽이 파이프 끊김으로 감지한다.

파이프 메시지 형식

struct MsgHeader { uint32_t magic = 'FPEV'; uint32_t type; uint32_t jobId; uint32_t bodyLen; };

enum MsgType : uint32_t { HELLO=1, ENROLL=2, ATTEMPT=3, COMPARE=4, QUIT=9, REPLY=100 };

struct ExtractReq { int32_t iType; int32_t width, height; wchar_t rawPath[260]; wchar_t outPath[260]; };
struct CompareReq { wchar_t enrollPath[260]; wchar_t attemptPath[260]; };

struct Reply {
  int32_t  status;        // Status enum (아래)
  int32_t  retVal;        // DLL 반환값 그대로
  int32_t  errCode;       // piErrorCode
  char     errMsg[256];   // arErrorMessage (NUL 보장 처리)
  int32_t  outSize;       // 템플릿 크기
  double   score;         // Compare 점수
  int64_t  elapsedUs;     // DLL 호출 시간만
  uint32_t sehCode;       // CRASH일 때 예외 코드
};

x86·x64 Worker가 같은 GUI와 통신하므로 구조체는 #pragma pack(push,1)와 고정 크기 타입만 쓴다(포인터·size_t 금지).

04Scheduler와 오류 처리

구조

  • EvalScheduler는 작업 큐 하나와 WorkerSlot N개를 가진다. 각 슬롯은 자기 스레드에서 "큐에서 꺼냄 → 요청 → 응답 대기 → 결과 기록"을 반복한다
  • 응답 대기는 overlapped ReadFile + WaitForMultipleObjects({readEvent, cancelEvent}, timeout)
  • 결과는 ResultStore(mutex로 보호)에 넘기고, 진행 정보는 GUI 창에 PostMessage(WM_APP_PROGRESS)로 알린다. 작업 스레드는 UI 객체를 직접 건드리지 않는다

WorkerSlot 상태 전이

stateDiagram-v2
  [*] --> Starting: CreateProcess
  Starting --> Ready: HELLO OK
  Starting --> Failed: 로드 실패
  Ready --> Busy: 작업 전송
  Busy --> Ready: 응답 수신 (OK/FAIL/MISMATCH)
  Busy --> Restarting: timeout → TerminateProcess
  Busy --> Restarting: 파이프 끊김 / CRASH 응답
  Restarting --> Starting
  Ready --> Stopped: 큐 비었음 → QUIT
  Busy --> Stopped: 강제 종료
  Stopped --> [*]

결과 상태 (Status enum)

상태언제지표 반영
OK반환 1, 출력 검사 통과점수 사용
FAIL반환 ≤ 0Enroll: NEF / Compare: NMF
TIMEOUT제한 시간 초과 (기본 10초, 설정 가능)FAIL과 동일 + 횟수 별도 표기
CRASH예외, 프로세스 비정상 종료FAIL과 동일 + 예외 코드 기록
MISMATCH반환 1인데 크기·점수가 규격 밖FAIL과 동일
OVERFLOW출력 버퍼 canary 훼손FAIL과 동일
SKIP_EF / SKIP_AF필요한 템플릿이 없어 호출 안 함NG,EF(·NI,EF) / NMF
ABORTED사용자 강제 종료 순간 진행 중집계 제외, 이어하기 때 다시 수행

강제 종료와 이어하기

  • 중지: 큐에 새 작업 배분을 멈추고 진행 중인 작업이 끝나기를 기다린다
  • 강제 종료: cancelEvent → 모든 Worker TerminateProcess, 진행 중이던 작업은 ABORTED
  • 이어하기: 결과 폴더를 열면 plan.json과 로그를 읽어, 로그에 OK~SKIP 상태로 남은 jobId는 건너뛰고 나머지만 실행. 같은 계획이므로 결과는 한 번에 돌린 것과 같다

병렬 실행 시 주의

  • Worker는 프로세스가 분리되어 있어 평가 대상 DLL이 스레드 안전하지 않아도 문제없다
  • COMPARE는 필요한 템플릿이 만들어진 뒤에만 실행되도록 STEP 3이 끝난 후 시작한다 (단계 사이 barrier)
  • 시간 측정은 Worker 안의 DLL 호출 구간만 재므로 병렬 수와 무관하게 비교 가능. 단, CPU 경쟁이 있으므로 리포트에 동시 수행 수를 함께 적는다

재현성 규칙

  • 난수는 std::mt19937_64 하나 (seed는 사용자 입력 또는 시각으로 생성 후 표시·저장)
  • std::shuffle, std::uniform_int_distribution은 컴파일러마다 결과가 다를 수 있으므로 쓰지 않고 Fisher–Yates와 정수 범위 변환을 직접 구현한다 (mt19937_64 자체 출력은 표준으로 고정)
  • 규칙마다 하위 seed를 seed ^ hash("genuine")처럼 파생해, 한 규칙을 바꿔도 다른 규칙 결과는 그대로 유지
  • "계획 저장"은 쌍 목록과 실행 순서를 그대로 파일로 저장, "계획 불러오기"는 이 파일을 읽어 STEP 2를 건너뛴다

무작위 순서의 목적

등록·비교 순서가 파일명 순이면 DLL이 "다음 비교는 같은 손가락"처럼 규칙을 유추할 수 있다. 그래서 STEP 3·4의 작업 순서를 섞고, Worker에 넘기는 경로에도 원본 파일명 대신 jobId 기반 이름(cache/000123.raw)을 쓰는 옵션을 둔다.

06지표 계산 방법

집계 변수

변수의미
N_Enroll, N_EF등록 시도 수, 등록 실패 수 (FAIL·TIMEOUT·CRASH·MISMATCH·OVERFLOW)
N_G, N_I계획에 정의된 전체 genuine / impostor 시도 수
N_G,EF, N_G,MF등록 실패로 못 한 genuine 수 / 비교 실패 genuine 수 (Attempt 추출 실패 포함)
gScores, iScoresOK인 genuine / impostor 점수 배열 (정렬해 둠)

계산

  • FMR(t) = |{s ∈ iScores : s ≥ t}| / N_I, FNMR(t) = (N_G,EF + N_G,MF + |{s ∈ gScores : s < t}|) / N_G — 정렬 배열에 이진 탐색으로 O(log n)
  • 후보 임계값 t: 모든 점수의 고유값 + 0 + (1+ε). 소수 3자리 점수이므로 0.000~1.000을 0.001 간격으로 돌아도 1,001개면 충분 → 두 방식 중 설정에서 선택
  • EER: FVC 정의(t1, t2 → EERlow, EERhigh의 중간) 기본, "가장 가까운 교차점" 방식 선택 가능
  • EER*: 분모를 OK인 시도 수(|gScores|, |iScores|)로 바꾸고 실패 항을 뺀 같은 계산
  • ZeroFMR = FMR(t)=0인 t 중 최소 FNMR, ZeroFNMR = FNMR(t)=0인 t 중 최소 FMR, FMR100/FMR1000 = FMR ≤ 1% / 0.1%인 t 중 최소 FNMR
  • 시간: 상태 OK인 작업의 elapsedUs 평균 (Enroll, Attempt, Compare 전체·genuine·impostor). 템플릿 크기: Enroll OK의 평균·최대

항목별 "적용 수식 선택"은 MetricOptions 구조체 하나에 모은다: FMR/FNMR 분모(사전 정의 수 / 실제 수행 수), EER 방식, 임계값 후보 방식, 점수 반올림 여부.

그래프 3종

그래프축표시 요소
DET Curvex: FMR, y: FNMR (둘 다 log, 10⁻⁵~1)곡선, y=x 대각선, EER 점, FMR100·FMR1000·FMR10000 세로선과 교차점. 0 값은 축 최솟값으로 클램프
Score Distributionx: 점수 0~1 (100구간), y: 비율genuine·impostor 히스토그램 반투명 겹침, 범례에 n 표기
FMR(t)·FNMR(t)x: 임계값, y: 오류율 0~100%두 곡선, EER 점과 t 값, 점선 세로선

그리는 방식

  • ICanvas 인터페이스(line, polyline, rect, text, setColor)를 두고, SvgCanvas(문자열로 SVG 작성)와 EmfCanvas(GDI+ Metafile에 그리기) 두 구현을 만든다
  • ChartRenderer는 축 계산·눈금·범례를 담당하고 ICanvas에만 그린다 → 같은 코드로 SVG와 EMF가 동시에 나온다

리포트 문서

  • 공통 구성: 표지(DLL 이름·해시·날짜·DB·seed·동시 수행 수) → 평가 설정 → 요약 지표 표 → 그래프 → 오류 목록(상위 50건) → 부록(쌍 수, 로그 파일 위치)
  • ReportModel(지표 + 설정 + 그래프 경로)을 만들고 IReportWriter가 형식별로 출력. 선택하지 않은 항목은 ReportModel 단계에서 빠진다
  • HTML: 하나의 파일, SVG를 <img src="figures/det.svg">로 참조
  • DOCX: [Content_Types].xml, _rels/.rels, word/document.xml, word/_rels/document.xml.rels, word/media/*.emf를 만들어 miniz로 zip. 표는 w:tbl, 그림은 w:drawing 인라인

09지문인식 DLL 동작

함수별 처리

KISA_Enroll / KISA_Attempt같은 추출 경로

  1. iType → (W, H) 확인, 모르는 iType이면 0 반환 + 에러코드 1
  2. pImage를 W×H 범위 안에서만 읽어 내부 Image(float)로 복사
  3. 정규화 → 분할(전경 마스크) → 방향장·주파수 → Gabor 강조 → 이진화 → 세선화
  4. 미뉴셔 추출 → 거짓 미뉴셔 제거 → 품질이 낮으면(미뉴셔 < 8개) 0 반환 + 에러코드 10
  5. 템플릿 직렬화해 pEnroll에 쓰고 크기 기록, 1 반환

모든 처리는 try { } catch (...)로 감싸 예외가 DLL 밖으로 나가지 않게 하고, 실패 시 0과 에러 메시지를 돌려준다.

KISA_Compare매칭

  1. 두 템플릿의 magic·version·count 검증 (손상 시 0 반환)
  2. 미뉴셔 쌍마다 회전·이동 후보를 계산해 Hough 누적 → 최다 득표 변환으로 정렬
  3. 거리·각도 허용 오차 안에서 1:1 대응 찾기 (탐욕적 매칭)
  4. 점수 = 대응 수² / (nE × nA) 등으로 정규화, [0,1]로 자르고 소수 3자리로 반올림

템플릿 형식

#pragma pack(push,1)
struct TemplateHeader { uint32_t magic = 'FPT1'; uint16_t version = 1; uint16_t width, height;
                        uint16_t count; uint8_t  quality; uint8_t reserved; };
struct Minutia        { uint16_t x, y; uint16_t angle; /* 0..359 */ uint8_t type; /* 1=끝점 2=분기 */ uint8_t quality; };
#pragma pack(pop)
// 전체 크기 = sizeof(TemplateHeader) + count * sizeof(Minutia)  (count ≤ 255 → 2KB 이하)

DLL 지켜야 할 것

  • 전역 가변 상태 없음 (스레드 안전), 함수 내부 지역 버퍼 또는 std::vector 사용
  • /MT로 정적 링크해 VC++ 런타임 의존을 없앤다 (시험 PC에 런타임이 없을 수 있음)
  • x86/x64 두 구성 모두 빌드, export 이름이 장식되지 않도록 extern "C" + .def 파일 사용
미정 사항: iType=2가 300×300(FVC2002)과 640×480(FVC2004) 두 가지라 DLL이 크기를 구분할 수 없다. 답변 전까지 iType→크기 표는 한곳(SensorTable.h)에만 두어 쉽게 바꿀 수 있게 한다.

14코딩 규칙과 테스트

코딩 규칙

  • C++17, 네임스페이스 fpe::(평가), fpa::(알고리즘). 클래스 PascalCase, 함수 camelCase, 멤버 m_ 접두사(MFC 관례)
  • 문자열은 내부 std::wstring(Windows API), 파일 출력은 UTF-8(BOM 없음, CSV는 Excel용 BOM 옵션)
  • new/delete 직접 사용 금지, std::unique_ptr·RAII 래퍼 사용
  • Core 라이브러리는 MFC 헤더를 include하지 않는다
  • 예외는 Core 내부에서만, Worker·DLL 경계 밖으로는 상태 코드로만 전달
  • 경고 수준 /W4, 경고 0개 유지. 외부 라이브러리는 third_party/에만 두고 LICENSES.md에 출처 기록
